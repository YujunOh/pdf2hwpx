# pdf2hwpx

디자인만 끝난 교재 PDF에 문제 텍스트와 수식을 채워 넣는다. 인쇄소에 그대로 내는 PDF와, 강사가 한글에서 고칠 HWPX를 함께 뽑는다.

인쇄용 PDF는 원본 디자인을 뜯지 않는다. 통째로 깔고 그 위에 글만 얹으므로 화질 손실이 0이다.

## 왜 만들었나

[indd2hwp](https://github.com/YujunOh/indd2hwp)를 먼저 만들었다. 디자이너가 InDesign으로 넘긴 산출물을 학원 한글 환경으로 옮기는 도구였는데, README에 한계를 이렇게 적어두고 끝났다.

> - PDF 변환 결과는 이미지 기반이라 한/글에서 본문 편집이 어렵습니다.
> - IDML은 텍스트 중심 추출이라 원본 레이아웃을 완전히 보존하지 않습니다.

레이아웃과 편집 가능성이 그때 배타적으로 갈렸다. PDF 경로는 레이아웃이 완벽한데 300dpi 이미지로 구워 넣어서 글자를 못 만지고, IDML 경로는 텍스트인데 `Spreads/*.xml` 의 좌표를 안 읽어서 레이아웃이 날아갔다.

이 저장소는 그 교집합을 만든다.

## 처음에 틀렸던 것

처음에는 PDF에서 벡터 도형을 전부 읽어 HWPX 네이티브 도형으로 다시 그렸다. 래스터화를 안 하니 무손실이라고 봤다. 그 전제가 틀렸다.

`get_drawings` 는 입력 단계에서 이미 버린다. `fill_shade`(그라데이션)와 `fill_image` 는 순번만 세고 데이터를 버리며, 소프트 마스크와 타일링 패턴 콜백은 아예 비어 있다. 삼각형 클립은 바깥 사각형으로 보고된다. 예외도 경고도 없다. 무손실이 아니라 조용한 손실이다.

만든 쪽이 그은 선이 이렇다.

> "it may still be unclear (and programmatically impossible to determine) which paths belong together and actually are part of a larger figure."
>
> 어떤 path들이 서로 묶여 실제로 더 큰 그림의 일부인지는 여전히 불분명할 수 있고, 프로그램으로 판정하는 것이 불가능하다.

— [Artifex 블로그](https://artifex.com/blog/extracting-and-creating-vector-graphics-in-a-pdf-using-python-pymupdf)

받는 쪽도 그릇이 아니었다. HWPX `CurveSegment` 의 필드는 `type, x1, y1, x2, y2` 가 전부다. 세그먼트당 좌표가 두 쌍인데 PDF의 3차 베지어는 제어점 둘에 끝점 하나로 세 쌍이 필요하다. 매핑이 수학적으로 불가능해서 직선 근사밖에 없었고, 실물 디자인 한 장에서 점이 7만 개가 됐다.

실물 PDF에서 도형 1093개 중 1046개가 Type3 폰트의 글자 외곽선이었다. 이것도 버그가 아니다. ISO 32000-1 §9.6.5가 Type3 글리프를 "그래픽 연산자의 스트림"으로 정의하고, MuPDF는 같은 글자를 외곽선으로 그리면서 텍스트로도 한 번 더 내보낸다. 추출이 되게 하려고 일부러 그런다.

우리가 겪은 증상은 전부 남들 트래커에 있었다. LibreOffice는 PDF 클리핑을 12년째 미구현으로 두고 있고([bug 86211](https://bugs.documentfoundation.org/show_bug.cgi?id=86211)), Inkscape는 구현했지만 파일 하나에서 클리핑 패스를 1120개 만든다([#5345](https://gitlab.com/inkscape/inkscape/-/issues/5345)). 우리 1093개와 자릿수가 같다.

가장 성숙한 오픈소스 PDF→워드 변환기 [pdf2docx](https://github.com/ArtifexSoftware/pdf2docx) 는 축 정렬 사각형이 아닌 벡터를 전부 288dpi 비트맵으로 굽는 것을 기본값으로 삼는다. 재구성을 시도조차 안 한다.

## 지금 어떻게 하나

```
레이아웃 PDF ──┬─ 원본 그대로 ────────────┬─ 인쇄용 PDF (손실 0)
               │                          │
               ├─ 슬롯 검출 ─┐            │
문제 원고    ──┴─────────────┴─ 조판 ─────┴─ HWPX (한글에서 편집)
```

산출물이 둘이고 역할이 다르다.

**인쇄용 PDF.** `show_pdf_page` 로 원본 페이지를 벡터 상태 그대로 깔고, 그 위에 강사 글을 얹는다. 원본을 뜯지 않으니 클리핑, 투명도, 그라데이션, 소프트 마스크, CMYK, 임베드 폰트가 전부 살아 있다. 굽는 단계가 없어서 dpi를 고를 일도 없다. 실물 디자인 한 장으로 확인한 결과가 209.9 x 297.0mm, **이미지 0개**, 177KB다.

**HWPX.** 강사가 원고를 손볼 때 쓴다. 최종 산출물이 아니라 편집 매개체다.

수식은 둘 다에서 살아 있다. HWPX에서는 `<hp:script>` 문자열이라 더블클릭하면 한글 수식 편집기가 열리고, PDF에서는 분수선과 근호까지 벡터로 조판된다. 미리보기와 인쇄물이 **같은 조판 엔진**을 지나므로 화면에서 본 대로 나온다.

**좌표.** HWPUNIT은 1pt가 정확히 100이다. PDF 좌표에 100을 곱하면 끝이라 반올림 손실이 없다.

**미리보기.** 원본 PDF를 화면 배율에 맞춰 굽는다. 확대하면 그 배율로 다시 구워서 문제 번호가 디자인 폰트 그대로 보인다. 같은 화면이면 캐시를 써서 타이핑 중에는 다시 굽지 않는다. 분석 123ms, 캐시 상태 다시 그리기 7.6ms.

`벡터 보기` 를 켜면 예전 방식으로 도형을 그린다. HWPX에 무엇이 나갈지 확인하는 용도로 남겼다.

## 빠르게 해보기

`pdf2hwpx.exe` 를 더블클릭합니다. 처음 열면 무엇을 해야 하는지 화면에 적혀 있습니다.

1. **찾아보기** 로 교재 PDF를 고릅니다. exe 위로 PDF를 끌어다 놓아도 됩니다.
2. 열면 문제 칸을 스스로 찾습니다. 잘못 잡히면 손으로 그리면 됩니다.
3. 빨리 보고 싶으면 오른쪽 **전체 예시** 를 누릅니다. 칸이 한 번에 채워집니다.
4. **Ctrl+P** 를 누릅니다. 인쇄용 PDF가 exe 옆 `out` 폴더에 생기고 바로 열립니다.

작업 파일(`.dhp`)은 없어도 됩니다. 하던 작업을 이어서 하고 싶을 때만 Ctrl+S 로 저장하고 Ctrl+O 로 엽니다.

한 번 연 PDF는 기억해 두었다가 다음에 첫 화면에서 바로 고를 수 있게 보여줍니다.

## 실행

파이썬 없이 쓰려면 [릴리스](https://github.com/YujunOh/pdf2hwpx/releases)에서 `pdf2hwpx.exe` 를 받아 더블클릭하면 됩니다. 레이아웃 PDF를 exe 위로 끌어다 놓으면 그 파일로 바로 시작합니다.

소스로 돌리려면 `실행.bat` 를 더블클릭하거나 이렇게 합니다.

```bash
pip install PyMuPDF pillow pywin32
python gui.py
```

직접 빌드하려면 `build.bat` 를 실행합니다. PyInstaller가 없으면 알아서 설치합니다.

쓰는 순서는 이렇다.

1. 레이아웃 PDF를 연다. 도형을 뽑고 문제 칸을 검출해 왼쪽 미리보기에 겹쳐 보여준다. 칸이 잘못 잡혔으면 손으로 고친다. 빈 곳을 끌면 새로 그려지고, 안쪽을 끌면 옮겨지고, 오른쪽 아래 모서리를 끌면 크기가 바뀌고, 오른쪽 버튼으로 지운다.
2. 선생님 원고를 불러온다. hwp, hwpx, txt를 읽어 문항과 수식을 뽑는다. 목록에서 두 번 누르면 고른 칸에 들어가고, 순서대로 채우기를 누르면 한 번에 배분된다.
3. 필요하면 손질한다. 달러 기호 사이가 수식이고 팔레트로 분수와 근호와 적분을 넣는다. 타이핑하는 동안 왼쪽 미리보기가 바로 갱신된다.
4. HWPX를 만든다. 한글로 열어 확인할 수도 있다.

작업은 `.dhp` 파일로 저장한다. PDF 경로와 칸 좌표와 각 칸의 원고가 들어간다.

### 단축키

한글에서 손이 익은 키를 그대로 가져왔다.

| 키 | 하는 일 |
|---|---|
| `F5` | 레이아웃 분석 |
| `Ctrl+Shift+O` | 원고 불러오기 |
| `Alt+I` | 원문자 순환. 3을 치고 누르면 ③, 한 번 더 누르면 ⑶ |
| `Ctrl+M` | 수식 넣기 |
| `Ctrl+Enter` | 다음 칸 |
| `Ctrl+P` | 인쇄용 PDF 만들기 |
| `Ctrl+B` | HWPX 만들기 |
| `F12` | 한글로 열어 확인 |
| `Ctrl+S` / `Ctrl+O` | 작업 저장 / 열기 |
| `F2` | 선택한 칸 확대 |
| `F9` | 로그 접기 |

프로그램 옆에 `keys.json` 이 생긴다. 고치면 바뀐다.

CLI만 쓰려면 이렇게 한다.

```bash
python pdf2hwpx.py      # problems.json을 읽어 out/에 hwpx 생성
python verify_hwp.py    # 한글로 열어 PDF로 내보내 검증
```

## 검증 결과

### 인쇄용 PDF (실물 디자인 PDF로)

| 항목 | 결과 |
|---|---|
| 페이지 크기 | 209.9 x 297.0 mm (원본과 동일) |
| 이미지 | **0개** — 래스터화 0회 |
| 파일 크기 | 177 KB (폰트 서브셋 후) |
| 생성 시간 | 131 ms |
| 텍스트 추출 | 250자 |
| 수식 | 분수, 적분, 근호, 시그마 전부 벡터 |

폰트를 서브셋하지 않으면 맑은 고딕 한 벌이 통째로 들어가 8.6MB가 된다. `subset_fonts()` 를 반드시 부른다.

### HWPX

한글 2024가 생성한 파일을 열었다. `Open` 이 True를 반환했고 문서에서 텍스트 272자가 추출됐다. 내보낸 PDF는 210 x 297mm 정확히 A4이고 벡터 21개에 **이미지 0개**다. 폰트는 본문 HCRBatang, 수식 HyhwpEQ로 잡혔다.

| 요구 | 결과 |
|---|---|
| 글씨가 깨지지 않을 것 | 원문자 ①~④, 위첨자 ², ³ 전부 살아남 |
| 이미지로 박히지 않을 것 | 내보낸 PDF에 이미지 0개 |
| 나중에 선택하고 편집할 것 | 한글에서 텍스트 272자 추출됨 |
| 수식 | 더블클릭하면 수식 편집기가 열림 |
| 원본 화질 | 래스터화 0회 |

## 문제 원고 형식

`problems.json` 을 고치거나 GUI에서 입력한다. `t` 가 일반 텍스트, `eq` 가 한글 수식 스크립트, `br` 이 줄바꿈이다.

```json
{
  "no": "001",
  "slot": 0,
  "parts": [
    {"t": "다음 극한값을 구하시오."},
    {"br": true},
    {"eq": " lim _{h ``rarrow`` 0} {f left(2+h  right)-f left(2  right)} over {h}"}
  ]
}
```

수식은 한글 수식 편집기 문법을 그대로 쓴다. `over` 가 분수, `sqrt` 가 근호, `int _{a} ^{b}` 가 적분이고 백틱이 좁은 공백이다. 한 낱말이 아홉자를 넘으면 편집기가 두 항으로 쪼개므로 큰따옴표로 묶어야 한다.

## 아직 안 되는 것

- 여러 쪽 한 번에 처리. 지금은 한 쪽씩이다. 문제 번호를 쪽을 넘겨 이어 붙이는 것도 없다.
- HWPX 쪽 배경. 인쇄용 PDF는 원본을 그대로 쓰지만, HWPX는 아직 도형을 다시 그린다. 배경을 300dpi 그림 한 장으로 바꾸는 것이 남았다.
- 좌표 스키마를 파일로 빼기. 슬롯 검출이 틀렸을 때 JSON만 고쳐 다시 돌리는 경로가 없다.
- 슬롯 검출 조건이 이 교재 디자인에 맞춰져 있다. 다른 디자인이면 손으로 칸을 그려야 한다.

## 원본 PDF에 관한 부탁

이 도구는 디자이너가 **InDesign에서 직접 내보낸 PDF**를 받을 때 가장 잘 동작한다.

우리가 받은 실물 파일은 `Producer` 가 PDFium이었고 폰트가 전부 이름 없는 Type3였다. 브라우저 인쇄나 PDFium 기반 도구를 한 번 거친 중간 변환본이라는 뜻이다. Skia는 TrueType이 아닌 폰트, 가변 폰트, 임베딩 불가 폰트, 그리고 외곽선이나 그림자가 걸린 글자를 전부 Type3로 떨어뜨린다.

InDesign 직접 내보내기를 받으면 글자가 글자로 남고, 글자 외곽선 1046개를 걸러낼 일도 없어진다.

`.idml` 도 함께 받으면 좋다. 텍스트 프레임 경계가 이름 붙은 객체로 들어 있어서 문제 칸 위치를 좌표 추론이 아니라 이름 읽기로 얻는다. 다만 필수는 아니다. 없어도 동작한다.

## 참고한 것

HWPX 내부 마크업은 OWPML이고 KS X 6101:2011 한국산업표준이다.

- [hancom-io/hwpx-owpml-model](https://github.com/hancom-io/hwpx-owpml-model) 한컴 공식 OWPML 모델. 태그와 속성과 enum의 사실상 스펙
- [neolord0/hwpxlib](https://github.com/neolord0/hwpxlib) HWPX 객체 모델. 도형 XML 실물 샘플을 여기서 얻었다
- [airmang/python-hwpx](https://github.com/airmang/python-hwpx) 순수 파이썬 HWPX. LaTeX 양방향 변환기가 있다
- [한컴테크 HWPX 포맷 구조](https://tech.hancom.com/hwpxformat/)
- [한글 수식 명령어 공식 도움말](https://help.hancom.com/hoffice/multi/ko_kr/hwp/insert/equation/equation(script).htm)

## 관련 저장소

- [indd2hwp](https://github.com/YujunOh/indd2hwp) 이 도구의 전작. InDesign 산출물을 한글로 변환하는 Tkinter GUI
